# Integration Tutorial: User Authentication

## 1. Overview

This tutorial demonstrates how to integrate with the authentication API of the Predictive Business Analytics platform.

It covers a complete authentication workflow:

1. Register a new user.
2. Log in using the registered credentials.
3. Obtain a JSON Web Token (JWT).
4. Access a protected endpoint using the token.

By completing this tutorial, developers will understand how to authenticate users and make authorized requests to the backend API.

## 2. Prerequisites

Before starting, ensure that:

- The backend is running locally, or the deployed API is accessible.
- Swagger UI is available.

**Local API:**

`http://localhost:3000`

**Deployed API:**

`https://predictive-business-analytics-backend.onrender.com`

**Local Swagger UI:**

http://localhost:3000/api-docs

**Deployed Swagger UI:**

https://predictive-business-analytics-backend.onrender.com/api-docs

The examples below use the local API.

## 3. Step 1 — Register a User

To create an account, send a POST request to:

`POST /api/auth/register`

**Request headers:**

```http
Content-Type: application/json
```

**Request body:**

```json
{
  "email": "integration-test@example.com",
  "password": "ExamplePassword123!"
}
```

The email must have a valid format. The password must contain between 8 and 128 characters.

**Expected response — HTTP 201 Created:**

```json
{
  "user": {
    "id": "b23ce7b8-5508-4ba5-a7da-069d937cdc5b",
    "email": "integration-test@example.com"
  },
  "token": "<jwt_access_token>"
}
```

The UUID and JWT are illustrative placeholders; actual values are generated by the server.

The API creates the user in PostgreSQL, securely hashes the password, and returns the public user information together with a JWT access token.

**Possible errors:**

| Status | Description                        |
| ------ | ---------------------------------- |
| 400    | Invalid registration data          |
| 409    | Email is already registered        |
| 429    | Authentication rate limit exceeded |

If the email is already registered, use another test email or proceed to the login step.

## 4. Step 2 — Log In

To authenticate an existing user, send:

`POST /api/auth/login`

**Request headers:**

```http
Content-Type: application/json
```

**Request body:**

```json
{
  "email": "integration-test@example.com",
  "password": "ExamplePassword123!"
}
```

**Expected response — HTTP 200 OK:**

```json
{
  "user": {
    "id": "b23ce7b8-5508-4ba5-a7da-069d937cdc5b",
    "email": "integration-test@example.com"
  },
  "token": "<jwt_access_token>"
}
```

The API verifies the credentials and returns an access token.

**Possible errors:**

| Status | Description                        |
| ------ | ---------------------------------- |
| 400    | Invalid login data                 |
| 401    | Invalid email or password          |
| 429    | Authentication rate limit exceeded |

For security reasons, the API does not reveal whether an incorrect email or password caused the authentication failure.

## 5. Step 3 — Use the JWT Access Token

The access token returned after successful registration or login is required for protected endpoints.

Include it in the HTTP Authorization header using the Bearer scheme:

```http
Authorization: Bearer <jwt_access_token>
```

The token is signed using HS256 and expires after the configured lifetime (2 hours by default).

The backend verifies the token before allowing access to protected resources.

**Security considerations:**

- Never share access tokens publicly.
- Never include real tokens in source code or Git commits.
- Use HTTPS when communicating with the deployed API.
- Handle expired or invalid tokens by requiring the user to authenticate again.
- The current API does not provide refresh-token or logout/revocation endpoints.

## 6. Step 4 — Retrieve the Authenticated User

After obtaining a valid JWT, send:

`GET /api/auth/me`

**Request header:**

```http
Authorization: Bearer <jwt_access_token>
```

**Expected response — HTTP 200 OK:**

```json
{
  "id": "b23ce7b8-5508-4ba5-a7da-069d937cdc5b",
  "email": "integration-test@example.com"
}
```

The endpoint returns the authenticated user's public information.

It does not return the password hash or access token.

**Possible authentication errors:**

| Status | Error message                           |
| ------ | --------------------------------------- |
| 401    | Authentication token is required        |
| 401    | Invalid authentication token            |
| 401    | Invalid or expired authentication token |
| 401    | User no longer exists                   |

An HTTP 401 response indicates that the request cannot be authenticated.

## 7. Testing the Workflow in Swagger UI

The complete workflow can be tested using the interactive Swagger UI.

**Register:**

1. Open https://predictive-business-analytics-backend.onrender.com/api-docs
2. Expand `POST /api/auth/register`.
3. Click **Try it out**.
4. Enter the registration JSON.
   {
   "email": "user@example.com",
   "password": "ExamplePass123!"
   }
5. Click **Execute** and confirm HTTP 201.

**Login:**

1. Expand `POST /api/auth/login`.
2. Click **Try it out**.
3. Enter the registered credentials. {
   "email": "user@example.com",
   "password": "ExamplePass123!"
   }
4. Click **Execute** and confirm HTTP 200.
5. Copy the returned JWT token.

**Authorize:**

1. Click **Authorize** in Swagger UI.
2. Paste the JWT into the Bearer authentication field.
3. Click **Authorize**, then **Close**.

Swagger UI automatically includes the Bearer authentication scheme in requests to protected endpoints.

**Get the user profile:**

1. Expand `GET /api/auth/me`.
2. Click **Try it out**.
3. Click **Execute**.
4. Confirm HTTP 200 and verify that the returned email matches the authenticated user.

## 8. Rate Limiting

Registration and login requests share a rate limit of 20 requests per IP address within a 15-minute window.

When the limit is exceeded, the API returns:

**HTTP 429 Too Many Requests**

```text
Too many requests, please try again later.
```

Clients should respect the `Retry-After` response header when provided and avoid repeatedly submitting authentication requests during the waiting period.

## 9. Workflow Summary

| Step                  | Method | Endpoint                   | Expected status |
| --------------------- | ------ | -------------------------- | --------------- |
| Register a user       | POST   | `/api/auth/register`       | 201             |
| Log in                | POST   | `/api/auth/login`          | 200             |
| Obtain JWT            | —      | Returned by Register/Login | —               |
| Retrieve user profile | GET    | `/api/auth/me`             | 200             |

This workflow demonstrates how to authenticate a user and access a protected API resource.

The same authentication mechanism can be reused for future protected endpoints, including server-side analytics and analysis history, once those endpoints are implemented.
